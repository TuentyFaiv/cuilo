---

title: Adopt and capture
description: Take over code you already have with cuilo adopt, or turn project files into a reusable piece of a local pack with cuilo pack capture.
---

Two commands connect cuilo to code that already exists. `cuilo adopt` records existing files as generated by a piece, so later updates merge into them. `cuilo pack capture` goes the other way: it turns files from your project into a new piece you can generate again under other names.

## Adopt existing code

Use [`cuilo adopt`](/reference/cli/adopt/) when your project has code that matches a piece: you wrote it by hand, copied it from the pack, or made it with another tool. It takes the same arguments as `cuilo add`:

```sh
cuilo adopt cards/card ProfileCard --from ./packs/cards --dry-run
```

```text
adopt cards/card
  nothing to change
Packages to add (offered after applying; --install adds them without asking):
  npm      clsx ^2.1
Notes:
  src/cards/profile-card.tsx: adopted with your differences; updates will merge into them
```

cuilo renders the piece with your inputs and looks at each file it would write:

- A file that exists is kept as it is. The lockfile records what the pack would have written as its original, and `.cuilo/` keeps a copy.
- A file that does not exist is created, as `cuilo add` would.

Patches the piece makes to other files are planned as with `cuilo add`, and a patch that is already in place changes nothing. The plan above changes no file, so applying it writes only the lockfile, as a transaction:

```text
Applied transaction 1 (0 file(s)). Undo it with `cuilo undo`.
```

Your differences from the pack now count as your edits:

```sh
cuilo status
cuilo why src/cards/profile-card.tsx:9
```

```text
modified  src/cards/profile-card.tsx
src/cards/profile-card.tsx:9 is yours: added or changed since generation; cards 1.0.0 piece `card`
```

When the pack releases a new version, `cuilo update` merges it into your file like any generated file. Here the pack added a `subtitle` prop, and the extra `"shadow"` class you had stays:

```sh
cuilo update cards --from ./packs/cards
```

```tsx
export function ProfileCard({ title, subtitle }: ProfileCardProps) {
	return (
		<article className={clsx("profile-card", "shadow")}>
			<h2>{title}</h2>
			{subtitle && <p>{subtitle}</p>}
		</article>
	);
}
```

See [Update generated code](/guides/updates/).

:::tip
Run `--dry-run` first. If the plan shows `create` for files you expected to adopt, the name or inputs don't match the paths your code uses, and cuilo would add new files instead.
:::

## Capture files as a piece

[`cuilo pack capture`](/reference/cli/pack/#cuilo-pack-capture) copies project files into a new piece of a local pack. `--piece` names the piece, and `--name` gives the spelling of the component's name in the files. That spelling becomes the piece's `name` input, so cuilo replaces it in every case form when you generate the piece again:

```sh
cuilo pack capture src/ui/user-card/user-card.tsx src/ui/user-card/user-card.module.css --piece card --name UserCard
```

```text
capture card into packs/local
  create  packs/local/pieces/card/files/user-card/user-card.tsx
  create  packs/local/pieces/card/files/user-card/user-card.module.css
  create  packs/local/pieces/card/piece.toml
  create  packs/local/pack.toml
```

Without `--name`, the piece has no `name` input and generates the files as they are.

The plan writes only inside the pack folder, `packs/local` by default. `--pack-dir` picks another folder, and `--pack` names a new pack (default `local`). A new `pack.toml` starts at version `0.1.0`, and it may write to the folder the files share:

```toml
schema_version = 1
name = "local"
version = "0.1.0"

[permissions]
write = ["src/ui/**"]
```

The piece's `target` is that shared folder. Folders named after the `--name` spelling, like `user-card/`, stay inside the piece, so they are renamed too.

The name needs two or more words, because a one-word name is replaced only where it is written exactly:

```text
error: cannot capture these files: capture: `Card` is one word, so it would only be replaced where written exactly `Card`; file names and other spellings would keep it. Use a name of two or more words, such as `SiteCard`
```

cuilo also refuses files that mention `@cuilo`, which pack templates reserve for directives. A piece that already exists is replaced only with `--force`.

### Generate the captured piece

Load the pack with `--from` and add the piece under a new name:

```sh
cuilo add card TeamCard --from ./packs/local
```

```text
add local/card
  create  src/ui/team-card/team-card.module.css
  create  src/ui/team-card/team-card.tsx
```

The original files are not tracked yet. To have later versions of the pack merge into them too, adopt them:

```sh
cuilo adopt card UserCard --from ./packs/local
```

### Capture into an existing pack

When the pack already has a `pack.toml`, cuilo leaves it alone. If its `permissions.write` does not cover the new files, the plan tells you what to add:

```text
Notes:
  packs/local/pack.toml: add `lib/hooks/**` to `permissions.write` so the pack may write this piece's files
```

After you change a pack that the project already uses, raise its `version` in `pack.toml`, since cuilo refuses a pack whose files changed under the same version. Then move the project to it:

```sh
cuilo update local --from ./packs/local
```

Until you do, `cuilo add --from ./packs/local` fails, because the lockfile pinned the old files:

```text
error: `path:./packs/local` changed: the lockfile pinned sha256:5e492cd3dac90e8d7795250d25c44a9f717c11720912d2ba0d46402ec9057b29, the source now has sha256:8b28b334e39e41a5186998523bf7507d85ae770adefb566b5160f9e802c7f98f
```

A captured piece is a plain copy of your files. To add optional code, variants or more inputs, edit it as described in [Write a pack](/packs/write-a-pack/).
